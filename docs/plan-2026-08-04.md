## 1. Full offline

### 1.1 Cel

Użytkownik bez internetu (po wcześniejszym udanym syncu) może:

1. **Przeglądać wszystkie listy i słowa** (treść kart z cache).
2. **Przenosić karty między listami**, w tym wrzucać z list użytkownika do **„Uczę się”**.
3. **Ćwiczyć SRS** (kolejka, ocenianie, typing/choice lokalnie).
4. **Dodawać nowe słowa przez wyszukiwanie (bez lookupu AI)** — trafiają na listę **„Oczekujące”** / EN **„Pending”** i po powrocie sieci są lookupowane / enrichowane.
5. Po odzyskaniu netu: **zsynchronizować** mutacje, progres SRS **oraz** kolejkę „Oczekujące” z serwerem bez utraty lokalnej pracy.

Poza zakresem tego feature’a (świadomie):
- **import / wklej tekst / plik / URL offline** — zablokowane (tylko online),
- tworzenie / rename / delete list offline (wyjątek: auto-utworzenie listy „Oczekujące”),
- zmiana ustawień offline (outbox settings),
- prawdziwy multi-candidate lookup offline (brak AI bez netu),
- auto-wrzucanie stubów prosto do „Uczę się”.

### 1.1a Offline search → lista „Oczekujące”

**Założenie:** offline nie ma lookupu AI. „Wyszukiwanie” = user wpisuje lemma i **odkłada ją do kolejki** na później.

#### Lista

| | PL | EN |
|--|----|-----|
| Nazwa (stała, jedna na profil) | **Oczekujące** | **Pending** |

- Jeśli listy nie ma → **utwórz od razu lokalnie** (i w outboxie create-list / przy syncu ensure po stronie).
- Jeśli jest → **dopisuj** stuby.
- To **zwykła lista usera** (nie `is_system`), auto-tworzona; po online user może przenieść słowa do „Uczę się”.

#### UI Home / Add (offline)

| Element | PL | EN |
|---------|----|-----|
| Banner / tytuł | Jesteś offline | You’re offline |
| Opis (zamiast „wpisz słowo albo zaimportuj listę”) | Dodane słowa trafią na listę „Oczekujące” i zostaną wyszukane, gdy znów będziesz online. | Added words go to the “Pending” list and will be looked up when you’re back online. |
| Placeholder pola | Wpisz słowo | Enter a word |
| Import / wklej / plik / URL | **Disabled**; snackbar: Import jest dostępny tylko online. | Import is only available online. |
| Pole search | **Działa** (focus, klawiatura, submit) | |

Online: bez zmian (hint z importem jak dziś).

#### Po submit offline (brak sheetu kandydatów)

1. Ensure lista „Oczekujące”.
2. Stub karty lokalnie: `lemma_l2` z inputu, bez gloss/POS (lub POS unknown).
3. Status: **`awaiting_network`** (osobny od `pending` enrichment AI).
4. Kafelek **wyszarzony**; chip statusu: **Czeka na sieć** / **Waiting for network**.
5. Brak expand enrichment / spinnera AI.
6. Snackbar: Dodano do „Oczekujące” — lookup po powrocie sieci. / Added to “Pending” — lookup when you’re back online.
7. Duplikat lemma na tej liście (ignore-case) → nie dodawaj; snackbar: To słowo już czeka na liście „Oczekujące”. / That word is already waiting on “Pending”.

#### Po powrocie netu

W `syncNow` (po push moves/reviews, przed lub po pull — preferuj: **po push mutacji, przed pełnym pull** albo zaraz po pull z lokalnymi stubami zachowanymi do przetworzenia):

1. Dla każdego stuba `awaiting_network` na „Oczekujące”:
   - `lookup` jak online search,
   - utwórz / podmień na prawdziwą kartę + enrichment (`pending` → `ready`) jak zwykłe dodanie,
   - usuń lokalny stub / oznacz jako resolved.
2. Brak kandydatów / fail → status `failed`, chip np. **Nie znaleziono** (lemma zostaje do ręcznej poprawki).
3. Lista „Oczekujące” zostaje (nie auto-kasować gdy pusta).

User nic nie klika — WorkManager / sync to ogarnia.

#### Rozróżnienie statusów

| Status | Znaczenie |
|--------|-----------|
| `awaiting_network` | Offline queue — brak lookupu |
| `pending` | Online — AI enrichment w toku |
| `ready` | Gotowa karta |
| `failed` | Lookup lub enrichment nieudany |

Stubów `awaiting_network` **nie** wrzucać do kolejki SRS (tylko `ready` + deck „Uczę się”).

### 1.2 Stan obecny (baseline)

Już istnieje i należy **rozszerzyć**, nie przepisywać:

| Warstwa | Co jest |
|---------|---------|
| Room | `cached_cards` (z `deckId`), `pending_reviews`, `local_settings`, `sync_meta` |

| Review sync | outbox → `POST /sync/push` (idempotentne `client_id`) → `GET /sync/pull` |

### 1.3 Docelowy model offline

```
UI (Home / Practice / Search)
  → LearningRepository (local-first)
      → Room mirror (cards, lists, pending_reviews, pending_mutations,
                     pending_lookups / stuby awaiting_network)
      → best-effort API
      → SyncScheduler / SyncWorker (CONNECTED)
Backend
  → POST /sync/push  (reviews + moves [+ create Pending list jeśli potrzeba])
  → lookup / create card  (flush awaiting_network)
  → GET  /sync/pull  (settings + lists + cards)
```

**Zasada syncu (obowiązkowa kolejność):**
1. Push lokalnego outboxa (moves, potem reviews — albo w jednej paczce z ustalonym porządkiem).
2. **Flush stubów `awaiting_network`** (lookup + create/enrich na serwerze; lokalnie → `pending`/`ready`/`failed`).
3. Dopiero potem pull.
4. Jeśli push fail → **nie robimy pull** (żeby nie nadpisać lokalnego postępu). Stubów lookup nie kasować przy failu pushu.
5. Po udanym syncu lokalny mirror = stan serwera (full replace OK na MVP); stuby jeszcze niezaflushowane muszą przetrwać pull (nie nadpisać ich destrukcyjnie — wyłączyć z full-replace albo merge po `awaiting_network`).

### 1.4 Konflikt: polityka

Założenie: równoległy offline na dwóch urządzeniach = rare / nie wspieramy UX-owo.

**Reguła: Last-Write-Wins per mutacja, chronologia po timestampie klienta + serwer jako źródło prawdy po syncu.**

| Mutacja | Rozwiązanie konfliktu |
|---------|------------------------|
| Review SRS | Oba review trafiają na serwer (idempotencja `client_id`). Aplikowane w kolejności `reviewed_at`. Stan FSRS = wynik po obu. Bez deduplikacji „tej samej karty”. |
| Move karty | Outbox z `client_id` + `moved_at`. Serwer: wygrywa **najpóźniejszy `moved_at`**. Wcześniejszy move jest pomijany / nadpisywany. |
| Stub „Oczekujące” | Idempotencja po `(profile, list Pending, lemma_norm)`; drugi offline add tej samej lemma = no-op. Po flushu zwykła karta na serwerze. |
| Po syncu | Pull zastępuje lokalny mirror (z ochroną niezaflushowanych stubów). Brak ekranu konfliktów. |

Nie robić: CRDT, merge list, „keep both”, ręcznego resolve w UI.

### 1.6 Kryteria akceptacji

1. Po syncu online → airplane mode:
   - Home pokazuje listy (w tym „Uczę się”) i słowa z cache.
   - Przeniesienie karty z listy usera → „Uczę się” działa lokalnie (karta znika z listy źródłowej, pojawia się w nauce / ma `deckId` null).
   - Practice ładuje kolejkę z Room i przyjmuje oceny bez netu.
2. Offline search:
   - widać komunikat o offline + liście „Oczekujące” / „Pending”,
   - import/wklej **niedostępne**,
   - wpisanie słowa tworzy/ dopisuje do „Oczekujące”; kafelek wyszarzony ze statusem „Czeka na sieć”,
   - duplikat lemma nie tworzy drugiego stuba.
3. Po włączeniu netu (bez ręcznego restartu apki, w rozsądnym czasie WorkManager / next sync):
   - pending moves i reviews znikają z outboxa,
   - stuby z „Oczekujące” przechodzą lookup/enrichment (`pending`→`ready` lub `failed`),
   - serwer ma ten sam `deck_id` i zaktualizowany SRS,
   - drugie urządzenie po syncu widzi ten sam stan (po flushu).
4. Stubów `awaiting_network` nie ma w kolejce Practice / SRS.
5. Ponowny push tego samego `client_id` (move lub review) nie duplikuje efektu.
6. Dwa move tej samej karty z różnym `moved_at` → na serwerze wygrywa nowszy.
7. Brak regresji: online path (listy, move, practice, search+import) działa jak dotychczas.

## 2. Listy — filtrowanie i sortowanie

### 2.1 Cel

W zakładce **Lists** user przegląda **jedną wybraną listę** i może:

1. Widzieć na kafelku **część mowy (POS)** obok istniejącego chipa stanu SRS.
2. **Filtrować** słowa w obrębie tej listy (POS + stan karty; opcjonalnie flagi „dziś”).
3. **Sortować** listę (lemma / POS / data / stan).

**Poza zakresem (świadomie):**
- Custom study / „Learn tylko z przefiltrowanych” — nie robimy; SRS zostaje na pełnej kolejce „Uczę się”.
- Chip nazwy listy na kafelku — redundantny (user już jest w liście).
- Drugi poziomy rząd chipów POS nad listą (filtr jest w modalu).
- Filtrowanie cross-list (wszystkie listy naraz).

### 2.2 Założenie produktowe

Kto naprawdę się uczy, trzyma się SRS. Filter/sort służą **przeglądaniu i organizacji listy**, nie obchodzeniu schedulera.

### 2.3 Stan obecny (baseline z kodu)

| Element | Stan |
|---------|------|
| Chipy list (góra) | `ListChip` w `HomeScreen` — wybór listy + count |
| Kafelek słowa | `ListWordTile` — lemma + `StatusChip` (SRS) / spinner `pending`; **brak POS** |
| POS w UI | `TagChip` + `localizedPosLabel` — używane w **search candidates**, nie na liście |
| Dane karty w liście | `GET /lists/{id}/words` → `CardResponse`: `pos`, `srs_status`, `srs_interval_days`, `created_at`, `enrichment_status` |
| Mapowanie statusu UI dziś | `new` → new; `learning`/`relearning` → learning; `review`+interval≥21 → mastered; **`review`+interval&lt;21 dziś też pokazuje label „learning”** — do poprawy przy tym featurze (patrz §2.5) |
| Filter / Sort UI | brak |
| `HomeViewModel` | trzyma `listWords` raw z API; brak stanu filtrów/sortu |
| Review „dziś” | `ReviewLog.reviewed_at` + `correct` / `SrsState.last_reviewed_at` — **nie są w `CardResponse` listy** |

Źródła: `HomeScreen.kt` (`ListWordTile`, `StatusChip`, `ListChip`), `HomeViewModel.kt` (`loadWords` / `listWords`), `Models.kt` (`CardResponse`), `learning.py` (`list_words`, `_card_response`), `Constants.kt` / `LocalizedPos.kt` (9 POS).

### 2.4 UX — layout

```
[ Learning N ⋮ ] [ inna lista ] [ + ]     ← rząd 1: listy (bez zmian)

N words · noun, adj          [Sort] [Filter]   ← rząd 2: meta + akcje
────────────────────────────────────────────
[ brać      noun                 new      ]
[ ładny     adj                  review   ]
```

- Rząd 2: po lewej liczba widocznych słów (po filtrze) + skrót aktywnych filtrów; po prawej **Sort** i **Filter**.
- Aktywny Filter: kropka / badge albo tekst „Filter · 2”.
- Sort/Filter otwierają **bottom sheet** (spójnie z innymi sheetami Home).
- Pusta lista po filtrze: empty state „No words match filters” + Clear filters.

### 2.5 Kafelek — chipy

Gdy dane są: **do dwóch chipów o różnych kolorach** (POS ≠ stan). Nie dokładamy trzeciego.

| Chip | Komponent | Kiedy |
|------|-----------|--------|
| POS | chip POS (`TagChip` lub wariant kolorów poniżej) | `pos` znane po normalizacji |
| Stan SRS | `StatusChip` | nie-pending; align z §2.6.2; błąd enrichment → `error` (wyjątek od pary poniżej) |

Chip listy na kafelku: **nie**.

**Ujednolicić label stanu** (teraz bug UX): `review` z interval &lt; 21 ma pokazywać **review**, nie „learning”.  
Mapowanie chipa = mapowanie filtra Card state (§2.6.2).

#### 2.5.1 Kolory chipów (obowiązkowe — różne pary per motyw)

POS i status **nie mogą** dzielić tego samego `primaryContainer`. Stała paleta:

| Motyw | Chip POS (tło) | Chip status SRS (tło) |
|-------|----------------|------------------------|
| **Light** | `#FFF5DC` | `#CAD3BB` |
| **Dark** | `#163A5C` | `#575D9A` |

Tekst (kontrast):

| Motyw | Tekst na POS | Tekst na status |
|-------|--------------|-----------------|
| **Light** | ciemny atrament (np. `#000000` / `onBackground`) | ciemny atrament |
| **Dark** | jasny krem (np. `#FFF5DC` / `onBackground`) | jasny krem |

Uwagi implementacyjne:
- Dodać tokeny w `Theme.kt` (np. `chipPosContainer` / `chipStatusContainer` + on-colors) — **nie** hardcodować ad hoc w `ListWordTile` bez nazwy.
- Search `TagChip` może zostać na `primaryContainer` **albo** przejść na kolor POS (`#FFF5DC` / `#163A5C`) dla spójności — decyzja przy implementacji; na **kafelku listy** obowiązuje tabela powyżej.
- Status `failed` (enrichment): nadal `error` / `#BF557F`, poza parą pastel/navy.

### 2.6 Modal Filter

Tytuł: **Filter**. Akcje: **Clear all** | **Apply**.

Logika łączenia: POS (OR wewnątrz) **AND** state (OR wewnątrz) **AND** każda włączona flaga „today”.  
Pusta sekcja multi-select = „wszystkie”.

#### 2.6.1 Part of speech — multi-select

Wartości kanoniczne (jak `POS_LABELS` / aliasy w `posLabel`):

| Wartość | Label UI (lokalizowane) |
|---------|-------------------------|
| `noun` | noun / rzeczownik / … |
| `verb` | verb |
| `adj` | adjective |
| `adv` | adverb |
| `prep` | preposition |
| `conj` | conjunction |
| `pron` | pronoun |
| `det` | determiner |
| `interj` | interjection |
| `unknown` | no POS |

**= 10 opcji** (9 POS + unknown).

Normalizacja przed porównaniem: te same aliasy co `posLabel` (`n`→`noun`, `a`→`adj`, …). Karty z `pos == null` / nierozpoznanym kluczem → bucket `unknown`.

#### 2.6.2 Card state — multi-select

| Wartość UI | Reguła |
|------------|--------|
| `new` | `srs_status == "new"` **lub** `srs_status == null` (brak SRS — traktuj jak new na liście nie-systemowej / pending edge) |
| `learning` | `srs_status in ("learning", "relearning")` |
| `review` | `srs_status == "review"` **i** `(srs_interval_days ?: 0) < 21` |
| `mastered` | `srs_status == "review"` **i** `(srs_interval_days ?: 0) >= 21` |

**= 4 opcje.**

Karty `enrichment_status == pending`: widoczne zawsze przy pustym filtrze state; jeśli state wybrany — tylko gdy pasują (zwykle `new`/null). Nie blokować filtrem enrichment w MVP (osobny wymiar odłożony).

#### 2.6.3 Today — toggles (faza 2 tego feature’a)

| Flaga | Label | Reguła |
|-------|--------|--------|
| `failed_today` | Failed today | dziś istnieje `ReviewLog` z `correct == false` **lub** `grade == again` (strefa czasowa usera / UTC — ustalić: **UTC day** na MVP) |
| `reviewed_today` | Reviewed today | dziś istnieje jakikolwiek `ReviewLog` dla karty **lub** `last_reviewed_at` jest dziś |

**= 2 flagi.** Wymaga rozszerzenia API (§2.8). W fazie 1 UI może ukryć sekcję Today.

### 2.7 Modal Sort

Single-select. Jedna aktywna opcja. **Apply** lub natychmiastowe zastosowanie po tapnięciu (preferuj natychmiast + dismiss).

| Wartość | Label | Kolejność |
|---------|--------|-----------|
| `lemma_asc` | A → Z | `lemma_l2` ignore-case |
| `lemma_desc` | Z → A | odwrotnie |
| `pos_asc` | Part of speech | kanoniczny POS A→Z, `unknown` na końcu; tie-break `lemma_asc` |
| `newest` | Newest first | `created_at` desc |
| `oldest` | Oldest first | `created_at` asc |
| `status` | Card state | kolejność: `new` → `learning` → `review` → `mastered`; tie-break `lemma_asc` |

**= 6 opcji.**  
**Default:** `lemma_asc` (stabilny przegląd; API dziś zwraca `created_at.desc` — po wejściu w listę aplikujemy default sort klienta).

## 3. Practice — Undo ostatniej oceny

### 3.1 Cel

Na ekranie Practice user może **cofnąć ostatnią ocenę** (Again / Hard / Good / Easy):

1. Przywrócić kartę i UI do stanu sprzed oceny.
2. Cofnąć lokalny FSRS + wpis outboxa (i na serwerze, jeśli już poszło).
3. Guzik **Undo** w **prawym górnym rogu**, na wysokości tytułu „Practice” (akcja `TopAppBar`).

Jak w Anki: **jedno cofnięcie** (ostatnia akcja w sesji), nie dowolna historia.

### 3.2 UX

```
[ ← ]  Practice                    [ ↶ Undo ]
────── progress bar ────────────────────────
         … karta …
[ Again ] [ Hard ] [ Good ] [ Easy ]
```

- Ikona cofnij (Material `Undo` / auto-mirrored) w `actions` TopAppBar.
- Enabled **tylko** gdy jest co cofać (`canUndo == true`).
- Disabled (wyszarzone) na starcie sesji, po udanym undo, po wyjściu z Practice.
- `contentDescription` / string `cd_undo` / `action_undo`.
- `testTag`: np. `TestTags.BTN_PRACTICE_UNDO`.

**Nie:** gesture / shake. Tylko przycisk.

### 3.3 Stan obecny (baseline z kodu)

| Element | Stan |
|---------|------|
| UI Practice | `PracticeScreen` → `AppScreenScaffold(title, onBack)` — **brak `actions`** w scaffoldzie |
| Ocena | `PracticeViewModel.grade()` → `repository.submitReview(...)` → `advanceToNext()` |
| Review path | **local-first**: `OfflineStore.applyReviewLocally` (LocalFsrs) + `pending_reviews` + best-effort `pushOutbox` / WorkManager |
| Idempotencja sync | `client_id` na `PendingReviewEntity` i `ReviewLog.client_id` (unique) |
| Online legacy | `POST /srs/review` nadal istnieje, ale Practice idzie przez outbox/`submitReview` |
| Cofanie FSRS | brak reverse w `LocalFsrs`; trzeba **snapshotu stanu sprzed `apply`** |
| Snapshot / undo stack | brak w ViewModel |

Źródła: `PracticeScreen.kt`, `PracticeViewModel.kt` (`grade`, `advanceToNext`), `AppScreenScaffold`, `LearningRepository.submitReview` / `pushOutbox`, `OfflineStore.applyReviewLocally`, `LocalFsrs`, `backend/.../sync.py` (push), `ReviewLog.client_id`.

### 3.4 Model undo (sesja)

W `PracticeViewModel` (pamięć sesji, nie Room):

```text
UndoFrame:
  clientId: String
  cardId: String
  previousSrs: snapshot pól SRS karty (status, intervals, FSRS fields, next/last review, lastGrade, …)
  queueIndex: Int          // index karty w kolejce w momencie oceny
  uiRestore:                 // stan UI potrzebny do powrotu na tę kartę
    answerMode, direction, lastCorrect, typedAnswer, choice selection, revealed, …
  pushedToServer: Boolean    // true jeśli outbox już usunął ten clientId po udanym push
```

- Po udanym `submitReview`: zapisz **jeden** `UndoFrame` (nadpisz poprzedni — tylko last-one).
- Po `undo()`: wyczyść frame → `canUndo = false`.
- `loadQueue` / wyjście z ekranu: wyczyść undo (nie cofamy po przeładowaniu całej kolejki / po kill procesu — akceptowalne MVP).

### 3.5 Flow: grade (zmiana względem dziś)

1. Zrób snapshot SRS z Room (`cardById`) **przed** `applyReviewLocally`.
2. Zrób snapshot UI + `currentIndex`.
3. `submitReview` jak dziś, ale **zwróć `clientId`** do ViewModel (dziś void).
4. Po sukcesie: `lastUndo = UndoFrame(...)`; `advanceToNext()`.

### 3.6 Flow: undo

1. Jeśli brak `lastUndo` → no-op.
2. **Lokalnie:**
   - Jeśli wiersz `pending_reviews` z tym `clientId` istnieje → **usuń** z outboxa (review nigdy nie trafi / nie duplikuje się na serwer).
   - Przywróć SRS karty w Room ze snapshotu (`cardDao.update` pełnym previousSrs).
3. **Serwer** (gdy wpis mógł już pójść — `pushedToServer` albo brak w outboxie mimo że grade był):
   - `POST /srs/undo` (lub `/sync/undo`) z `{ client_id, previous_srs }` — patrz §3.7.
   - Best-effort: jak netu nie ma, zapisz `pending_undos` **albo** prostszy MVP: oznacz frame jako „needsServerUndo” i wyślij przy następnym sync (patrz decyzja poniżej).
4. **UI:** ustaw `currentIndex = queueIndex`, przywróć `uiRestore`, wywołaj przygotowanie karty (jak `prepareCard` ale bez utraty restored fields). Progress bar cofa się o jeden krok.
5. Wyczyść `lastUndo`.

**Decyzja MVP (rekomendowana):**  
Undo działa w 100% lokalnie zawsze (Room + outbox).  
Jeśli review już wypchnięty: od razu wołaj API undo; przy braku netu — kolejkuj `pending_undo` (1 wiersz) i dołącz do `syncNow` **przed** push reviews (żeby nie re-pushować cofniętego). Alternatywa prostsza na start: undo **tylko gdy jeszcze w outboxie**; jeśli już synced → toast „Already synced, can’t undo” — **nie preferowane**; lepiej pełne undo z API.

Rekomendacja planu: **pełne undo** (local + API), z jednoelementowym outboxem undo przy offline.

### 3.7 Backend

Nowy endpoint, np.:

`POST /srs/undo`  
Body: `{ "client_id": UUID, "previous_srs": SyncSrsState }`  
(albo previous fields bez card_id duplikatu)

Zachowanie:
1. Znajdź `ReviewLog` usera po `client_id`. Brak logu → 200 idempotent (już cofnięte / nigdy nie doszło) — i tak ustaw `SrsState` na `previous_srs` jeśli karta należy do usera.
2. Jeśli log istnieje: **usuń** `ReviewLog`.
3. Ustaw `SrsState` karty na wartości z `previous_srs` (client snapshot). Walidacja: `card_id` z previous == log.card_id / body; karta `user_id` == current user.
4. Response: potwierdzenie + aktualny `SyncSrsState`.

Dlaczego snapshot z klienta, nie replay FSRS wstecz: LocalFsrs/py-fsrs nie mają taniego inverse; snapshot sprzed oceny jest źródłem prawdy dla jednego undo (spójne z Waszym LWW / zaufaniem do klienta przy rare multi-device).

**Nie** dodawać undo do `POST /srs/review` legacy bez `client_id` — Practice i tak używa outboxa. Opcjonalnie: przy `submitReview` / sync push upewnić się, że każdy review ma `client_id` (już ma).

## 4. Popraw kartę — zgłoszenie AI + edycja własna (fork)

### 4.1 Cel

AI czasem się myli; bez możliwości poprawy karty power userzy (Anki) nie zostaną.

User może:

1. **Zgłosić błąd** na karcie (multi-select sekcji + wolny tekst w dowolnym języku).
2. Dostać **werdykt LLM**: zasadne → karta poprawiona; niezasadne → opcja **edycji na własną odpowiedzialność**.
3. Przy edycji własnej: **prywatna kopia / fork** contentu (nie psuje wspólnego słownika innych userów).

**Poza zakresem (MVP):**
- pełny JSON editor contentu,
- natychmiastowa zmiana wspólnego `LexicalEntry` dla wszystkich userów po jednym zgłoszeniu,
- blokowanie SRS na czas zgłoszenia,
- offline submit zgłoszenia (wymaga netu; offline → disable + snackbar),
- community / voting na poprawki.

### 4.2 Założenia produktowe / dane

- Treść: `LearningCard.content` (+ opcjonalnie shared `LexicalEntry`).
- **Accepted (MVP):** patch dotyczy **LearningCard zgłaszającego**; odłączyć / skopiować entry (`lexical_entry_id` null lub prywatna kopia), żeby nie psuć cudzych kart.
- **Rejected → edycja własna:** fork contentu na tego usera (`user_edited`); shared entry nietknięty.
- Shared `LexicalEntry` update „dla wszystkich” = **poza MVP** (później: confidence / admin / próg).
- Status zgłoszenia **osobny** od `enrichment_status` (np. pole `content_review_status` lub tabela `card_corrections` + chip z ostatniego stanu).

### 4.3 Wejście UI

Akcja **„Popraw kartę”** / **„Fix card”** dostępna z:
- detail karty / expand na liście,
- tył fiszki w Practice (gdy treść widoczna),

nie zasłaniając Again/Hard/Good/Easy.

### 4.4 Modal 1 — Zgłoszenie

**Tytuł:** Popraw kartę / Report a problem  

**Multi-select (sekcje składowe karty)** — ≥1 wymagane **lub** niepusty note (preferuj: ≥1 sekcja **albo** note ≥ N znaków):

| Id sekcji | Label (EN / PL orientacyjnie) |
|-----------|-------------------------------|
| `lemma` | Lemma / Forma hasłowa |
| `pos` | Part of speech / Część mowy |
| `gloss` | Primary gloss / Główne tłumaczenie |
| `meanings` | Meanings / Znaczenia |
| `examples` | Examples & usages / Przykłady i użycia |
| `conjugation` | Conjugation / Odmiana |
| `similar` | Similar words / Distractors / Podobne słowa |
| `pronunciation` | Pronunciation / IPA / Wymowa |
| `other` | Other / Inne |

**Pod spodem:** `OutlinedTextField` — wolny tekst, dowolny język.  
Placeholder: *Opisz błąd…* / *Describe what’s wrong…*

**Submit** → loading; disable double-submit.  
Rate limit (backend): np. N zgłoszeń / user / dzień.

### 4.5 API + job AI

`POST /cards/{card_id}/corrections`  
Body: `{ "sections": ["gloss", "examples"], "note": "..." }`  
Response: `{ "correction_id", "status": "reported" }`

1. Walidacja: karta należy do usera; sections ∈ enum; note max length.
2. Zapis `card_corrections` (user_id, card_id, sections, note, status=`reported`, timestamps).
3. UI: chip / status **`correction_reported`** — „Zgłoszono poprawkę” / „Correction reported”.
4. Background job:
   - input: aktualny `content` + sections + note + L1/L2 profilu,
   - LLM: werdykt `accepted` | `rejected` + opcjonalny patch JSON **tylko** zaznaczonych sekcji + krótki `reason`,
   - walidacja patcha schematem contentu (jak enrichment); odrzuć niebezpieczne pola.
5. Jeśli `accepted`: zastosuj patch na `LearningCard`; ustaw status `accepted`; odśwież gloss_primary/pos jeśli trzeba; detach shared entry (MVP).
6. Jeśli `rejected`: status `rejected` + `reason`; **nie** zmieniaj contentu.

Opcjonalnie: `GET /cards/{id}/corrections/latest` do pollingu wyniku.

### 4.6 Modal 2 — Wynik zgłoszenia

Pokazać po pushu / przy kolejnym otwarciu karty gdy status ≠ reported (badge na „Popraw kartę”).

#### A) Accepted

- Tytuł/status: **Zgłoszenie uznane — kartę zaktualizowano.** / **Report accepted — card updated.**
- Body: krótki `reason` (opcjonalnie).
- CTA: **OK** → zamknij, odśwież content na UI.

#### B) Rejected

- Status: **Zgłoszenie uznane za niezasadne.** / **Report not accepted.**
- Body: `reason` + tekst:  
  **Możesz zedytować kartę samodzielnie — na własną odpowiedzialność. Powstanie Twoja prywatna kopia.**  
  / **You can edit the card yourself — at your own risk. This creates your private copy.**
- CTA: **Anuluj** | **Edytuj samodzielnie** / **Edit myself**

### 4.7 Modal 3 — Edycja własna (fork)

1. `POST /cards/{id}/fork-edit` (lub ten sam correction flow z `action=self_edit`):
   - klon / in-place: content skopiowany, `lexical_entry_id` odpięty lub prywatny entry,
   - status contentu: **`user_edited`** — „Edytowana ręcznie” / „Edited manually”.
2. Modal edycji (MVP — uproszczone pola, nie surowy JSON):
   - lemma, POS (dropdown z 9 wartości), gloss primary,
   - meanings (prosty multi-line / lista gloss),
   - opcjonalnie: przykłady jako tekst (parse best-effort) — albo tylko gloss+POS+lemma w v1.
3. **Zapisz** → `PATCH` contentu forka; zamknij; odśwież UI.
4. SRS / `card_id` / przynależność do listy: **zachować** (in-place preferowane), żeby nie gubić postępu.

### 4.8 Statusy (chip / pole)

| Status | UI (PL) | UI (EN) |
|--------|---------|---------|
| `none` / null | (brak chipa) | |
| `correction_reported` | Zgłoszono poprawkę | Correction reported |
| `correction_accepted` | Poprawiono | Updated *(krótko, potem można schować)* |
| `correction_rejected` | Zgłoszenie odrzucone | Report rejected |
| `user_edited` | Edytowana ręcznie | Edited manually |

Nie blokować Practice samym `correction_reported`.

## 5. Tryb mówienia — STT przy wyszukiwaniu (Add)

> Odpowiada pozycji z backlogu użytkownika: **#7 Tryb mówienia**.

### 5.1 Cel

W zakładce **Add** obok pola search: ikona **mikrofonu**. Tap → modal nasłuchiwania. Rozpoznana mowa (L1 **lub** L2 z aktywnej pary) trafia do istniejącego flow lookup / offline „Oczekujące”.

### 5.2 Stan obecny (baseline z kodu)

| Element | Stan |
|---------|------|
| Add search UI | `HomeScreen` `AddTab`: `OutlinedTextField` + `leadingIcon` Search + `trailingIcon` **tylko** strzałka submit (`onSearch`) — **brak mikrofonu** |
| TTS (output) | `TtsSpeak.kt` / `L2TtsSpeaker` — **mówienie do usera**, nie STT |
| STT / SpeechRecognizer | **brak** w projekcie |
| Uprawnienia | Manifest: `INTERNET`, `ACCESS_NETWORK_STATE` — **brak** `RECORD_AUDIO` |
| Lookup | `repository.lookup(query)` — tekst; działa dla L1 i L2 (backend już rozróżnia kierunek) |
| Offline search | plan #1: submit lemma → lista Oczekujące (STT może karmić ten sam submit) |

### 5.3 UX

```
[ 🔍  Wpisz słowo…                    🎤 ] [ → ]
```

- Mikrofon w `trailingIcon` **obok** submit (Row dwóch IconButton) albo mikrofon zamiast drugiego rzędu — preferuj: **mic + arrow** w trailing.
- Tap mic → **modal / bottom sheet „Słucham…”** (nie od razu systemowy intent bez UI).
- W modalu:
  - wybór języka rozpoznawania: **L2** (default) | **L1** (chipy / segmented) — etykiety z nazwami języków pary,
  - duża ikona mic / animacja „listening”,
  - live partial text (opcjonalnie),
  - Stop / Anuluj.
- Po finalnym wyniku: zamknij modal → ustaw `query` + wywołaj `onSearch` (ten sam pipeline co Enter).

#### Decyzja: czy pokazywać usłyszany tekst w input?

**Tak — rekomendacja:** wstaw rozpoznany tekst do `OutlinedTextField` **i** odpal lookup.

Dlaczego:
- user widzi / poprawi literówkę STT przed dodaniem,
- spójne z klawiaturą,
- offline path też dostaje widoczny lemma.

Opcja „od razu szukaj bez pokazania w polu” — gorsza (brak kontroli błędu STT).

### 5.4 Technicznie (Android)

- [ ] Permission `RECORD_AUDIO` + runtime request (Android 6+); rationale stringi.
- [ ] `SpeechRecognizer` + `RecognizerIntent.ACTION_RECOGNIZE_SPEECH` (on-device / Google), `EXTRA_LANGUAGE` = locale L1 lub L2 z profilu (`native_lang` / `learning_lang` → BCP-47).
- [ ] Fallback: jeśli STT niedostępne → dialog „Rozpoznawanie mowy niedostępne na tym urządzeniu”.
- [ ] Offline sieciowy ≠ offline STT: bez netu Google STT może nie działać — wtedy komunikat; **nie** mylić z offline lookup (#1).
- [ ] Nie blokować istniejącego TTS.
- [ ] Test tags: `BTN_VOICE_SEARCH`, sheet listening.

**Backend:** bez zmian (zwykły string query).

### 5.5 Poza zakresem

- Dyktowanie całych list / import głosowy.
- STT w Practice (odpowiedzi głosowe) — osobny feature później.
- Własny model Whisper na urządzeniu (MVP = system SpeechRecognizer).

### 5.6 Kryteria akceptacji

1. Na Add widać mikrofon obok pola search.
2. Po zgodzie na mikrofon: modal słuchania; wybór L1/L2.
3. Po rozpoznaniu tekst pojawia się w input i leci lookup (online) / enqueue Oczekujące (offline wg #1).
4. Odmowa permission → nie crash; wyjaśnienie.
5. Brak regresji: ręczne wpisywanie + strzałka search.

### 5.7 Kolejność prac

1. Permission + mic icon w AddTab trailing.
2. Listening modal + SpeechRecognizer (L1/L2).
3. Podpięcie wyniku do `query` + `onSearch`.
4. Stringi + edge (brak STT, deny permission) + QA.

### 5.8 Pliki

- `HomeScreen.kt` (AddTab), ewentualnie `VoiceSearchSheet.kt`
- `AndroidManifest.xml` — `RECORD_AUDIO`
- `HomeViewModel.kt` — tylko jeśli stan mic w VM
- `strings.xml`, `TestTags.kt`

### 5.9 Definicja „done”

§5.6 przechodzi na urządzeniu z działającym STT; status → **done**.

## 6. Push — przypomnienia nauki + gotowość kart

> Odpowiada pozycji z backlogu użytkownika: **#10 Przypomnienia / push**.

### 6.1 Cel

Gdy user **nie ma otwartej apki**, dostać powiadomienia m.in.:

1. **Karty gotowe** — było `pending` enrichment / `correction_reported` (lub `awaiting_network` po flushu) → teraz `ready` / poprawka rozstrzygnięta.
2. **Przypomnienie o nauce** — są due w SRS / streak / stała pora dnia (ustawienia).

### 6.2 Stan obecny (baseline z kodu)

| Element | Stan |
|---------|------|
| FCM / push | **brak** (backend i Android) |
| Lokalne Notification | **brak** kanałów / `NotificationCompat` |
| Permission | brak `POST_NOTIFICATIONS` (Android 13+) |
| WorkManager | tylko **sync** (`SyncScheduler` / `SyncWorker`) |
| Polling enrichment | **tylko gdy apka żyje**: `HomeViewModel.startPollingIfNeeded`, `LearningViewModel` — po zamknięciu **nic nie sprawdza** |
| Device tokens | brak modelu / endpointu |
| Settings UI | brak toggle „przypomnienia” / godziny nauki |

### 6.3 Typy powiadomień (MVP)

| Id | Kiedy | Tytuł / body (orientacyjnie) | Deep link |
|----|--------|------------------------------|-----------|
| `cards_ready` | ≥1 karta przeszła `pending`→`ready` (lub correction accepted) gdy apka w tle | „Karty gotowe” / „N gotowych słów do nauki” | Lists / Learning |
| `correction_resolved` | Zgłoszenie #4 accepted/rejected | „Sprawdzono poprawkę” | karta |
| `study_reminder` | Zaplanowana pora **i** `due_count > 0` (lub zawsze soft nudge) | „Czas na powtórkę” / „N kart czeka” | Practice |

Faza 2: weekly summary, streak at risk — nie blokuje MVP.

### 6.4 Architektura (rekomendacja)

Dwa toru (oba potrzebne):

**A. Lokalne (AlarmManager / WorkManager)** — przypomnienie nauki o wybranej godzinie; nie wymaga FCM.  
Czyta lokalny Room due count (po #1 offline mirror) albo lekki ping API jeśli online.

**B. Push FCM (data/notification)** — serwer wie, że enrichment/correction job skończył się gdy client nie polluje.  
Wymaga: `device_tokens`, `POST /devices/register`, worker po `enrich_card` / correction job → send FCM.

MVP minimalne ścieżki:
1. **Study reminder** — lokalny WorkManager daily (szybsze do shipowania).
2. **Cards ready** — FCM z backendu po enrichment **albo** okresowy `EnrichmentCheckWorker` (15–60 min) gdy są `pending` i apka nie na foreground — bez FCM na start, z FCM jako target.

**Rekomendacja w doku:**  
- Reminder nauki = lokalne.  
- Gotowość kart / correction = **FCM** (polling w tle alone jest zawodny i żre baterię).  
Ship można rozłożyć: 6a lokalne reminder, 6b FCM ready.

### 6.5 Ustawienia usera

W Settings (nowa sekcja **Powiadomienia**):

- [ ] Toggle: Przypomnienia o nauce (default ON po zgodzie systemu)
- [ ] Godzina przypomnienia (time picker; default np. 19:00 lokalnie)
- [ ] Toggle: Karty gotowe / poprawki (default ON)
- [ ] Runtime `POST_NOTIFICATIONS` na Android 13+

Bez zgody systemu → toggles OFF + wyjaśnienie.

### 6.6 Backend (dla FCM / cards ready)

- [ ] Tabela `device_tokens` (user_id, token, platform, updated_at).
- [ ] `POST /devices/register`, `DELETE /devices/{token}`.
- [ ] Po `enrich_card` → `ready` / `failed`: enqueue push do ownera karty (debounce: batch „N kart gotowych” w oknie 30–60 s, nie spam per karta).
- [ ] Po resolution correction (#4): push `correction_resolved`.
- [ ] Konfiguracja FCM credentials w env (nie w repo).
- [ ] Preferencje push w `UserSettings` (study_reminder_enabled, cards_ready_enabled, reminder_hour) — sync z klientem.

### 6.7 Android checklist

- [ ] Notification channels: `study`, `cards`.
- [ ] `POST_NOTIFICATIONS` permission flow.
- [ ] FCM dependency + `FirebaseMessagingService` (data payload → lokalna notyfikacja).
- [ ] Register token po login; unregister na logout.
- [ ] `StudyReminderWorker` / exact alarm wg godziny z settings.
- [ ] Deep link / Intent → Practice lub Lists.
- [ ] Settings UI toggles + time.
- [ ] Nie pokazywać notyfikacji gdy apka już na foreground i user widzi wynik (opcjonalnie suppress).

### 6.8 Poza zakresem MVP

- iOS (jeśli kiedyś) — osobny track.
- Marketing push / promo.
- Email zamiast push.
- Rich media / bundling beyond simple batch.

### 6.9 Kryteria akceptacji

1. User włącza przypomnienie + godzinę → o tej porze (apką zamknięta) dostaje notyfikację; tap → Practice / Home.
2. Po dodaniu słowa i zamknięciu apki: gdy enrichment skończy → notyfikacja „karty gotowe” (FCM lub uzgodniony worker); tap → lista.
3. Po zgłoszeniu poprawki (#4) i zamknięciu: notyfikacja o werdykcie.
4. Wyłączenie toggle w Settings → brak danego typu push.
5. Brak permission → brak crash; brak nieskończonego spamu (debounce batch).
6. Logout → token wyrejestrowany.

### 6.10 Kolejność prac

1. Channels + permission + Settings toggles (UI).
2. Lokalny study reminder (WorkManager).
3. Backend device tokens + FCM send helper.
4. Hook enrichment / correction → batched push.
5. Android FCM service + deep links.
6. QA: zabita apka, brak zgody, debounce.

### 6.11 Pliki (orientacyjnie)

**Android:**
- Manifest permissions, `google-services` / FCM gradle
- `ui/settings/SettingsScreen.kt` (+ ViewModel)
- nowy `notifications/` (channels, FCM service, reminder worker)
- `LearningRepository` / auth logout → unregister

**Backend:**
- `models` device_tokens + settings flags
- `api/v1/devices.py` (nowy)
- hook w `card_jobs.enrich_card` + correction job
- config FCM

### 6.12 Definicja „done”

MVP: lokalne przypomnienie nauki **oraz** co najmniej jedna ścieżka „karty gotowe” przy zamkniętej apce (FCM preferowane); AC §6.9; status → **done**.  
Jeśli FCM opóźnione: oznacz 6b w tabeli osobno — nie domykaj całego #6 bez gotowości kart.
